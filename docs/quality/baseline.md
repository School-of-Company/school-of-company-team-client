# 디자인 품질 기준선 (단계 1 F1)

기존 화면 전부를 계획 3.7의 5번 항목으로 점검한 결과입니다. 이후 단계는 이 표를 회귀 기준으로 씁니다.

- 기준 시점: `origin/main` `8548fd7` → 브랜치 `feat/s1-fe-quality`
- 확인 방법: 격리 스택(프론트 3101, backend 18081 = 서버 `origin/main` `9b9091e`, Postgres 15431)의 실제 API. 시드는 API 호출로만 만들었습니다.
- 스크린샷: `pnpm e2e screens`(`E2E_SCREENSHOT_DIR` 지정 시)가 라이트·다크 × 1440·390으로 찍습니다. 로딩·오류 화면은 보드 API 요청을 멈추거나 끊어서 재현했고, 응답을 지어내지 않았습니다.
- 자동 검증: `pnpm e2e`(격리 스택 필요). 폴링 깜빡임, 모바일 메뉴 키보드 동작, 키보드만으로 상태 바꾸기는 `e2e/board.e2e.ts`가 확인합니다.

표기: **통과**(처음부터 맞음) · **수정**(이 브랜치에서 고침) · **해당 없음** · **보류**(이유를 적음)

## 보류와 한계

- **pending(승인 대기)·connect-discord 실제 상태**: 두 화면은 GitHub OAuth로 가입한 계정에서만 나옵니다(legacy 비밀번호 계정은 대기 중 로그인이 거부되고, Discord 연결을 요구받지 않음). 격리 스택에서는 GitHub 로그인을 할 수 없어 거절·중지 상태만 실제로 찍었습니다. 승인 대기·Discord 연결 화면의 실계정 확인은 계획 B5(사람 GitHub 로그인)로 남깁니다.
- **오류 문구 중복**: 비참여자가 프로젝트를 열면 제목("프로젝트를 찾을 수 없거나 접근할 수 없습니다")과 서버 메시지("프로젝트를 찾을 수 없습니다.")가 거의 같습니다. 서버 응답 문구라 이 브랜치에서는 고치지 않았습니다.
- **legacy 계정의 Discord 요구**: 서버 AccessGate와 맞춰 GitHub 미연결 비밀번호 계정은 Discord 연결 없이 업무 화면에 들어가게 했습니다. 운영 OAuth 모드는 서버가 이런 계정의 토큰을 거부하므로 운영 동작은 그대로입니다.
