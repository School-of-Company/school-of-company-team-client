# Engineering Hub MVP 확정 명세

기준일: 2026-11-18. 이번 대화의 합의와 승인된 추천안을 통합한다. 제품 범위는 이 문서를 기준으로 하며 `plan.md`, `mvp-v2.spec.md`, `mvp-github-draft.md`는 이전 결정과 조사 근거 기록이다. 구현 완료 문서가 아니다.

## 목표와 선택

내부 팀이 아이디어를 검토하고 업무로 확정해 공동 배정·개발·논의·완료까지 관리한다. 프로젝트 없는 팀 공용 업무와 비공개 개인 업무도 같은 서비스에서 관리한다.

**자체 칸반 + GitHub Issue·PR 연동 + 디스코드 봇**으로 확정한다. GitHub Projects 직접 사용은 기본 역할·저장소 권한을 우리 요구와 동일하게 강제할 수 없으므로 채택하지 않는다. Projects 기반 자체 화면과 양방향 보드 동기화도 중복 편집·충돌 처리가 늘어나므로 제외한다. 공식 문서 비교 근거는 `mvp-github-draft.md`에 보존한다.

업무 내용·상태·담당자의 원본은 서비스, Issue·PR과 코드 리뷰는 GitHub, 대화는 Discord다. 기존 코드와 호환 가능한 부분은 재사용하되 기존 구현으로 제품 범위를 제한하지 않는다.

## 계정과 초기 운영

- GitHub OAuth로 가입·로그인한다. 신규 사용자는 승인 대기이며 헤드 어드민이 승인·거절·이용 중지를 관리한다.
- 승인 전에는 상태 안내만 제공한다. 승인 후 디스코드 계정을 연결해야 업무 기능을 이용할 수 있다. 연결 해제 후에도 기존 업무는 보존하고 재연결 화면으로 안내한다.
- 최초 헤드 어드민은 운영자가 지정한 GitHub 숫자 ID 한 개로 초기화한다. 최초 가입자를 자동 관리자로 승격하지 않는다. 초기 관리자도 디스코드 연결을 수행한다.
- 전공은 선택 프로필 정보이며 권한을 부여하지 않는다. 프로젝트 파트와 독립적으로 관리한다.
- 기존 자체 로그인 계정을 GitHub 사용자명·이름만으로 자동 병합하지 않는다. 기존 데이터가 있으면 검증된 운영자 매핑을 수행한 뒤 전환한다.

## 프로젝트·파트·권한

- 프로젝트 생성·최초 공개 설정·PM 지정은 헤드 어드민만 가능하다. 기본 공개 범위는 참여자만 공개다.
- 팀 전체 공개 프로젝트는 활성 팀원 전원이 조회 가능하다. 참여자만 공개 프로젝트는 참여자와 헤드 어드민만 조회 가능하다.
- PM은 프로젝트당 한 명. 헤드 어드민만 지정·교체·해제하며 기존 PM은 참여자로 남는다. 헤드 어드민은 PM이 없어도 관리한다.
- 헤드 어드민·해당 PM이 참여자·파트·파트 리더·공개 범위·연동 채널·연결 저장소를 관리한다.
- 파트 리더는 기존 프로젝트 참여자 중 자기 파트의 구성원을 배정·해제한다. 프로젝트에 외부 사용자를 추가하거나 다른 파트의 구성을 바꾸지 못한다.
- 프로젝트마다 파트를 만들고 한 참여자는 여러 파트에 속할 수 있다. 파트별 리더는 한 명으로 시작한다. PM·파트 리더 겸임은 허용한다.
- 아카이브와 복원은 헤드 어드민·해당 PM이 한다. 아카이브된 프로젝트는 조회만 허용하고 기본 보드·내 보드에서는 제외한다.
- 참여자 제외·이용 중지 시 작성 업무와 기록은 보존한다. 해당 사용자의 배정을 해제하고 남은 담당자를 유지한다. 담당자가 없어지면 미지정으로 표시한다. PM 제외는 먼저 교체·해제해야 한다.
- 파트 삭제 시 업무는 유지하고 해당 파트 배정만 해제한다.

| 대상 | 조회 | 등록·수정·담당 배정·상태 변경 | 삭제 |
| --- | --- | --- | --- |
| 프로젝트 업무 | 프로젝트 공개 범위에 따름 | 참여자·해당 PM·헤드 어드민 | 접근 가능한 작성자·해당 PM·헤드 어드민 |
| 팀 공용 업무 | 모든 활성 팀원 | 모든 활성 팀원 | 작성자·헤드 어드민 |
| 개인 업무 | 본인 | 본인 | 본인 |

파트 리더에게 별도 전체 삭제 권한을 주지 않는다. 헤드 어드민도 타인의 개인 업무를 열람하지 못한다. 업무 수정에 기본 승인 절차를 두지 않으며 특수 결재 엔진은 제외한다.

## 업무와 보드 기본값

- 제목만 필수(최대 200자), 설명·파트·마감일·담당자는 선택. 우선순위는 P0~P3, 기본 P2다. 업무 담당 파트는 최대 하나다.
- 담당자는 여러 명 또는 미지정. 프로젝트 참여자·전체 활성 팀원 중 범위에 맞게 선택한다. 개인 업무는 본인으로 고정한다.
- 상태는 검토 필요 → 진행 예정 → 진행 중 → 리뷰 → 완료. 기본은 검토 필요이며 등록자가 시작 상태를 지정한다. 수정 권한자는 앞뒤로 자유롭게 변경할 수 있다.
- 일반 업무(TASK)는 리뷰를 건너뛰며 리뷰 상태에 둘 수 없다. 개발 업무(DEV)는 리뷰 가능하다. 기본 타입은 TASK다.
- 막힘은 상태와 별도이며 사유 입력이 필수다. 완료 진입 시 완료 시각 기록, 완료에서 나오면 해제한다.
- 첫 구현에서는 기존 API·DB 값 BACKLOG를 검토 필요의 내부 코드로 유지하고 PLANNED를 진행 예정으로 추가한다. 나머지는 IN_PROGRESS·REVIEW·DONE이다. 기존 BACKLOG 데이터는 검토 필요로 취급하며 일괄 삭제·재생성하지 않는다.
- 내 보드는 내가 담당한 팀 업무·개인 업무를 출처와 함께 표시한다. 개인 업무만 필터링 가능하다. 동일 업무를 복제하지 않는다.
- 필터: 프로젝트·담당자·파트·상태·마감일·우선순위·타입·막힘. 같은 축은 OR, 다른 축은 AND. 조회 조건은 URL에 보존한다.
- 그룹핑: 없음·담당자·파트. 복수 담당자는 각 담당자 그룹에 같은 업무로 표시하되 총 업무 수는 고유 업무 기준이다.
- 컬럼 내 수동 순서와 상태 이동을 제공한다. 다른 정렬에서는 순서 드래그를 비활성화한다.
- 완료 컬럼은 레인당 처음 50개, 전체 개수와 더 보기를 제공한다. 화면 조회는 우선 10초 폴링이며 실시간 소켓은 제외한다.
- 업무 삭제 시 외부 Issue·PR·Discord 대화를 삭제하지 않는다. 외부 연결은 자동 재생성하지 않는다. 개인↔팀 업무 전환은 정보 공개가 바뀌므로 MVP에서 제외한다.

## GitHub 발행과 개발 연결

- 조직·저장소 관리 권한자가 GitHub App을 설치한다. PM은 설치에 허용된 저장소만 프로젝트에 연결한다. 한 프로젝트에 여러 저장소, 기본 발행 저장소 하나를 선택할 수 있다.
- 프로젝트 업무마다 발행 저장소를 선택하거나 없음으로 둘 수 있다. 기본 저장소는 신규 업무 선택 기본값일 뿐 모든 기존 업무를 발행하지 않는다.
- 검토 필요에서는 Issue를 발행하지 않는다. 발행 저장소가 있는 업무가 진행 예정 이상으로 생성·변경되면 최초 한 번 발행한다. 건너뛰기·되돌리기·재시도에도 기존 Issue를 재사용한다.
- 진행 중 이후 업무에 처음 발행 저장소를 지정하는 경우에도 발행 조건을 검사한다. 검토 필요에서 지정하면 착수까지 대기한다.
- 팀 공용·개인 업무는 자동 발행하지 않는다. 기존 주 Issue가 있으면 재사용하며 참고 링크와 구분한다.
- 제목·설명·업무 링크와 배정 가능한 GitHub 사용자를 초기 전달한다. 실행자의 원본 저장소 권한도 검사한다. 권한 부족 시 상태는 보존하고 발행 실패 및 해결 방법을 표시한다.
- 발행 뒤 저장소 변경은 제한하며 제목·본문·담당자 수정, 완료·재개방을 양방향 동기화하지 않는다.
- 기존 Issue·PR 연결과 원본 상태 조회를 제공한다. 하나의 업무에 여러 링크와 주 Issue 하나를 둔다. PR merge만으로 자동 완료하지 않는다.
- 기존 Issue 가져오기는 명시적으로 수행하고 제목·본문·매핑 가능한 담당자를 초기 복사한다. 같은 프로젝트의 같은 주 Issue는 기존 업무를 반환한다.
- 비공개 원본은 사용자별 원본 접근을 확인한 뒤 표시한다. 첫 출시의 비공개 Issue 가져오기는 본인 개인 업무에만 본문 복사를 허용한다. 공유 프로젝트에서는 링크 연결로 제한한다. 공개 원본은 프로젝트 업무로 가져올 수 있다.
- 가져온 개인 업무도 외부 원본 권한 철회 시 원본에서 복사한 정보는 숨기고 재인증을 안내한다. 권한 확인이 실패하면 외부 정보는 반환하지 않는다.
- 이벤트는 서명·중복·역순을 처리하고 누락은 재조회로 복구한다. 외부 작업은 DB에 영속 요청을 저장하고 발행 중·성공·실패·결과 확인 필요 상태를 표시한다. 응답 유실 시 확인 없이 재발행하지 않는다.

로그인 OAuth와 설치 권한을 분리하고 GitHub App 최소 권한을 사용한다. Issues 생성에 필요한 쓰기 권한 외에 불필요한 저장소 쓰기를 요청하지 않는다.

## 디스코드 논의

- 헤드 어드민이 팀 공용 채널, 헤드 어드민·PM이 프로젝트 채널을 지정한다. 봇 접근 가능한 채널만 선택한다.
- 팀·프로젝트 업무의 논의 버튼 최초 클릭으로 스레드를 만들고 업무 링크를 게시하며 담당자 전원을 멘션한다. 이후에는 동일 스레드로 이동한다. 등록만으로 생성하지 않는다.
- 개인 업무에는 버튼을 제공하지 않는다. 채널 미설정·권한 부족·실패 시 원인과 재시도를 안내하고 업무는 유지한다.
- 기존 스레드가 있는 업무에 담당자가 추가되면 새 담당자만 한 번 멘션한다. 스레드가 없으면 최초 생성 시점 담당자만 멘션한다.
- 봇을 통한 메시지 발송은 사용자 지정 본문에서 임의 멘션이 실행되지 않도록 제한하고, 지정한 담당자만 멘션한다.
- 비공개 프로젝트는 관리자 설정 과정에서 Discord 채널 공개 범위도 확인해야 한다. 다른 팀원에게 공개된 채널은 연결하지 않는다. Discord 역할 자동 배정·제거는 MVP에서 제외하며 채널 관리자 운영 절차를 명시한다.
- 공개 범위·참여자 변경이 Discord 권한까지 자동 변경한다고 표시하지 않는다. 공개 범위 축소 시 연결을 비활성화하고 관리자가 기존 채널·스레드 권한 정리를 확인한 뒤 다시 연결한다. 기존 대화를 이동·삭제하지 않는다.
- 스레드 삭제 시 자동 재생성하지 않고 관리자가 명시적으로 복구한다. 보관된 스레드는 원본 링크를 유지하며 재개방 가능 여부를 확인해 안내한다. 채널 변경도 기존 연결을 자동 덮어쓰지 않는다.
- 공유 채널에는 비공개 GitHub 원본 제목·본문을 자동 게시하지 않는다. 채널 접근 검증·스레드 API 지원 범위·복구 동작은 실제 봇 시험을 출시 조건으로 둔다.

## 화면과 핵심 동작

| 화면 | 핵심 동작 | 빈 상태·실패 |
| --- | --- | --- |
| 로그인·진입 | GitHub 로그인 → 승인 안내 → Discord 연결 → 내 보드 | 승인 거절·중지·연결 실패 원인과 재시도 |
| 내 보드 | 담당 업무·개인 업무 조회, 개인 업무 생성, 출처로 프로젝트 이동 | 업무 없음 안내·등록 버튼 |
| 팀 공용 보드 | 공용 업무 생성·공동 배정·드래그·필터 | 빈 컬럼에도 생성 가능 |
| 프로젝트 목록·보드 | 접근 가능한 프로젝트, 파트·담당자 필터, 업무 생성 | 비참여자는 수정 UI 없음, 서버에서도 거부 |
| 업무 상세 | 내용·복수 담당자·상태·막힘·마감·Issue/PR·디코 논의 | 발행 상태·권한 부족·연동 실패를 개별 표시 |
| 프로젝트 설정 | 공개 범위·참여자·PM·파트·저장소·채널·아카이브 | PM 지정은 헤드 어드민만 가능 |
| 관리자 | 승인·거절·중지·조직 사용자·프로젝트 생성 | 마지막 활성 헤드 어드민 제거 차단 |
| 내 계정 | 이름·전공·GitHub 식별·Discord 연결 상태 | 계정 토큰·봇 비밀값은 표시하지 않음 |

업무 생성은 현재 보드의 범위를 기본값으로 한다. 외부 발행을 유발하는 상태·저장소 선택에는 발행 예정 안내를 표시하되 매번 별도 승인 모달을 요구하지 않는다. 클릭 중·중복 요청·오류 메시지·키보드 조작을 화면 구현 기준에 포함한다.

## 제외 범위

공지·서비스 댓글·첨부파일·개인 업무 공유 전환·공동 PM·범용 승인·규칙 엔진·GitHub Projects 동기화·PR 생성·CI 집계·자동 merge 완료·스프린트·배포 대시보드·일반 알림 센터·실시간 소켓은 제외한다. Discord와 GitHub의 대화·코드 리뷰를 활용한다.

## 개발 순서와 검증

이 저장소는 서버 코드다. 화면은 제품 명세이며 실제 프론트엔드 구현은 프론트 저장소 위치를 확인한 뒤 진행한다. 서버가 완성돼도 화면 검증 전 MVP 전체 완료로 보고하지 않는다.

| 순서 | 작업 | 통과 기준 |
| --- | --- | --- |
| 1 | 5단계 상태·생성 시 상태 지정 | 선택 컬럼 배치·기본값·일반 업무 리뷰 거부·완료 시각·상태 이동 API 검증 |
| 2 | DB 전환 기반·프로젝트 역할·파트·접근 제어 | 기존 데이터 보존, 공개/비공개 권한과 조회 누출 차단 통합 테스트 |
| 3 | 팀 공용·개인 업무·복수 담당자·내 보드 | 모든 담당자 동일 업무 조회, 타인 개인 업무 차단, 배정·미배정 검증 |
| 4 | GitHub 로그인·승인·Discord 연결 | 최초 관리자·승인 전 차단·OAuth 실패·계정 탈취/자동 병합 방지 검증 |
| 5 | GitHub App·Issue 발행·PR 연결 | 실제 시험 저장소에서 최초 발행·중복·응답 유실·권한 철회 검증 |
| 6 | Discord 봇·스레드·멘션 | 실제 시험 채널에서 최초 클릭·재접속·중복·접근 변경·실패 복구 검증 |
| 7 | 화면 연결·운영 준비 | 전체 사용자 흐름, 권한별 화면, 백업·복구·재배포 검증 |

DB 전환은 버전 관리 마이그레이션을 도입하고 자동 DDL과 동시에 운영하지 않는다. 운영 데이터가 있으면 백업·복원 및 변환 결과를 확인한 뒤 전환한다. 기존 인증은 새 인증의 통합 테스트가 통과하기 전에 제거하지 않는다.

## 출시 기준과 외부 준비

- 프로젝트 생성 → 참여자·파트 배정 → 검토 업무 등록 → Discord 논의 → 진행 예정·Issue 발행 → PR 연결 → 리뷰 → 완료를 실제 팀원이 수행한다.
- 프로젝트 비참여자·중지 사용자·타인의 개인 업무와 비공개 외부 자료가 목록·검색·상세·캐시·알림을 통해 노출되지 않는다.
- 외부 장애 중 업무가 유실되지 않고 재시작 후 대기 작업·연결을 복구한다. Issue·스레드 중복과 실패 상태를 운영자가 해결할 수 있다.
- 실제 프론트·서버 연결, 접근 제한, 데이터 백업·복원과 비밀값 설정을 확인한다.

제품 결정을 위한 추가 인터뷰는 끝낸다. 외부 준비는 GitHub 조직/설치 대상, OAuth 설정, Discord 서버·봇·채널, 배포 주소, 최초 관리자 ID, 프론트 저장소 위치다. 비밀값은 문서·대화에 기록하지 않고 환경 설정으로 공급한다. 외부 준비 없이 가능한 서버 구현·통합 테스트는 먼저 진행하며, 실제 연동을 검증하지 않은 채 출시 완료로 표시하지 않는다.
